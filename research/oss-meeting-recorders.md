# Open-source meeting recorders / note-takers: landscape and echo-bleed handling

Researched 2026-10-11 against live GitHub data (`gh` CLI, shallow clones of each repo, Apple SDK headers, Apple forums). Stars / pushed dates are as of that day. Code citations use `blob/HEAD` links, so line numbers drift as repos move. They were checked on the cloned HEAD of 2026-10-11.

Provenance labels: **[code]** I read the file. **[README]** the project claims it; I did not verify it. **[inferred]** my reading of the evidence. **[unverified]** no source found.

## TL;DR

1. **Echo-handling depth is inversely related to stars.** Meetily (31.6k) has no AEC. The answers to our question sit in the small repos: pasrom/meeting-transcriber (200), Biscotti (184), Parrot (101), heed (18), plus Muesli and anarlog.
2. **The only project that does what we plan** (two tracks saved, AEC afterwards with `system` as reference, then ASR/diarization) is [pasrom/meeting-transcriber](https://github.com/pasrom/meeting-transcriber). Its stack is Core Audio process tap, a bundled LocalVQE neural AEC, an echo-bleed detector, a self-check, and embedding quarantine. It ships the AEC **off by default**.
3. **Recommendation:** capture the mic **raw** (no VoiceProcessingIO), and run **LocalVQE v1.4-AEC post-hoc** on `mic.wav` with `system.wav` as reference. Gate it on a bleed detector, and pick the delay by cross-correlation first. Use text-dedup only as a fallback and never stack the two. Details are in "Echo cancellation approaches".
4. **Counter-evidence you should know about.** heed measured WebRTC AEC3 (realtime, via LiveKit) *hurting* the user's own voice on 12 recordings, and text-dedup won ([ECHO_TUNING.md](https://github.com/isjunrod/heed/blob/HEAD/eval_echo/ECHO_TUNING.md)). pasrom shipped LocalVQE but kept it default-off because 11 or so recordings is not a soak. We need our own A/B on our recordings before trusting any of this.

## Per-project notes

### Meetily (31.6k)
- **Capture** is a global mono Core Audio process tap ([`core_audio.rs` L86-L122](https://github.com/Zackriya-Solutions/meetily/blob/HEAD/frontend/src-tauri/src/audio/capture/core_audio.rs#L86)). Comments there warn that adding the sub-device on top of the tap "creates duplicate audio (echo issue)". That is a duplicate-capture bug, not acoustic echo. [code]
- **Mixing:** raw mic and system chunks are mixed downstream and only the mix is saved. [`pipeline.rs` L591, L631](https://github.com/Zackriya-Solutions/meetily/blob/HEAD/frontend/src-tauri/src/audio/pipeline.rs#L591) says "No gain applied... prevents amplifying system audio bleed-through in the microphone", and the raw streams are not saved. So bleed is only dodged by not boosting the mic. [code]
- **Noise:** RNNoise via `nnnoiseless` ([`Cargo.toml` L97-98](https://github.com/Zackriya-Solutions/meetily/blob/HEAD/frontend/src-tauri/Cargo.toml#L97)) and EBU R128 loudness. No AEC, no VPIO, no speex. [code]
- Latest release v0.4.1 (2026-09-12). Not useful as an echo reference; useful only as the #1-by-stars reality check.

### screenpipe (21.9k, source-available)
- **Software AEC** is `SonoraAecProcessor` in [`core/aec.rs`](https://github.com/screenpipe/screenpipe/blob/HEAD/crates/screenpipe-audio/src/core/aec.rs#L1), a pure-Rust port of WebRTC audio processing ([dignifiedquire/sonora](https://github.com/dignifiedquire/sonora), BSD-3, 91 stars, pinned by git rev in [`Cargo.toml` L67](https://github.com/screenpipe/screenpipe/blob/HEAD/crates/screenpipe-audio/Cargo.toml#L67)). Config: 16 kHz mono, 10 ms frames, AEC3 plus "VeryHigh" noise suppression and AGC2 ([L40-L66](https://github.com/screenpipe/screenpipe/blob/HEAD/crates/screenpipe-audio/src/core/aec.rs#L40)), `set_stream_delay_ms` hint of 60 ms. [code]
- **Alignment:** timestamped mic and speaker queues. It aligns within 10 ms by draining the older queue, caps each queue at 1 s ("stale audio is worse than bypassing"), and falls back to a "bypass mode" (NS and AGC only) when there is no speaker data ([L149-L260](https://github.com/screenpipe/screenpipe/blob/HEAD/crates/screenpipe-audio/src/core/aec.rs#L149)). [code]
- **Defaults:** `macos_input_vpio_enabled: false` and `screenpipe_aec_enabled: false` ([`recording.rs` L378-384, L956-957](https://github.com/screenpipe/screenpipe/blob/HEAD/crates/screenpipe-config/src/recording.rs#L378)). Both are "experimental / opt-in". [code]
- **VPIO safety net:** [`vpio_health.rs`](https://github.com/screenpipe/screenpipe/blob/HEAD/crates/screenpipe-audio/src/device/vpio_health.rs#L1) documents that VPIO "can create an input stream successfully yet never deliver a single sample", and demotes a device to plain HAL after 3 deaths with a 120 s reset window. VPIO is only used on the system default input. [code]
- **Useful fact for us** ([`meeting_audio/macos.rs` L44-L48](https://github.com/screenpipe/screenpipe/blob/HEAD/crates/screenpipe-audio/src/core/meeting_audio/macos.rs#L44)): "for a process doing echo cancellation (VPIO)... CoreAudio lists the *output* device used as the AEC reference in the input scope too." That is evidence about how VPIO sees its reference (see the VPIO section).
- Diarization uses pyannote segmentation + embedding ONNX models ([`speaker/models.rs`](https://github.com/screenpipe/screenpipe/blob/HEAD/crates/screenpipe-audio/src/speaker/models.rs#L23), [`embedding_manager.rs`](https://github.com/screenpipe/screenpipe/blob/HEAD/crates/screenpipe-audio/src/speaker/embedding_manager.rs)). I did not trace voiceprint persistence. Latest release app-v2.7.104.
- License is "Other" (source-available). Do not copy code without reading it.

### anarlog (ex-Hyprnote, 9.5k)
- **Mic AEC** is a neural 2-stage ONNX model in [`crates/aec`](https://github.com/fastrepl/anarlog/tree/HEAD/crates/aec) (`model_{128,256,512}_{1,2}.onnx`, block 512 / shift 128 per [`onnx/model.rs`](https://github.com/fastrepl/anarlog/blob/HEAD/crates/aec/src/onnx/model.rs)). The two-stage + 512/128 structure matches DTLN-aec, but the repo does not name the source. **[inferred]**
- **Pipeline** ([`audio-actual/src/capture/stream.rs`](https://github.com/fastrepl/anarlog/blob/HEAD/crates/audio-actual/src/capture/stream.rs#L30)): an aligner searches mic-vs-speaker lag up to `AEC_MAX_REFERENCE_LAG_MS` = 600 ms, with `AEC_MIN_REFERENCE_OVERLAP_MS` = 400 and `AEC_MIN_REFERENCE_CORRELATION` = 0.12 (the last gates the linear-subtract stage) ([L30-L39](https://github.com/fastrepl/anarlog/blob/HEAD/crates/audio-actual/src/capture/stream.rs#L30)). After the NN it applies `cancel_linear_echo` ([L685-L745](https://github.com/fastrepl/anarlog/blob/HEAD/crates/audio-actual/src/capture/stream.rs#L685)), a smoothed least-squares gain subtract of the speaker reference. Its gain is estimated robustly (trimmed segment gains) when the residual ratio indicates double-talk. [code]
- **Headphone gate:** AEC is disabled when every playing output is headphones, because it "burns CPU and can degrade near-end speech" ([`listener-core/.../stream.rs` L48-L72](https://github.com/fastrepl/anarlog/blob/HEAD/crates/listener-core/src/actors/source/stream.rs#L48)). This matches the heed finding that AEC can hurt when there is no echo. [code]
- **Diarization:** `pyannote-local` crate (segmentation + clustering, `KnownSpeaker`, `SpeakerIdentity`, `assign_words`) ([`lib.rs`](https://github.com/fastrepl/anarlog/blob/HEAD/crates/pyannote-local/src/lib.rs)); changelog 1.4.17 (2026-09-03) "Separate speakers during on-device batch transcription" ([changelog](https://github.com/fastrepl/anarlog/blob/HEAD/packages/changelog/content/desktop/1.4.17.md)). Latest release desktop_v1.4.30.

### OpenOats (2.6k)
- **VPIO is hard-disabled.** `let useAEC = false` with the comment "AEC (voice processing) conflicts with system audio capture on macOS - both cause CoreAudio aggregate-device reconfiguration that can stall the mic stream" ([`TranscriptionEngine.swift` L525-L531](https://github.com/yazinsai/OpenOats/blob/HEAD/OpenOats/Sources/OpenOats/Transcription/TranscriptionEngine.swift#L525)). The code path to enable it still exists ([`MicCapture.swift` L79-L84](https://github.com/yazinsai/OpenOats/blob/HEAD/OpenOats/Sources/OpenOats/Audio/MicCapture.swift#L79)), and the setting defaults to true but is ignored. [code]
- **Transcript-level dedup** is [`AcousticEchoFilter.swift`](https://github.com/yazinsai/OpenOats/blob/HEAD/OpenOats/Sources/OpenOats/Transcription/AcousticEchoFilter.swift#L14). A mic utterance is dropped if it follows a system utterance within 1.75 s, has Jaccard word-set similarity >= 0.78 (or substring containment), and has at least 4 words or 20 characters ([L18-L21](https://github.com/yazinsai/OpenOats/blob/HEAD/OpenOats/Sources/OpenOats/Transcription/AcousticEchoFilter.swift#L18)). It is applied live in [`TranscriptStore.swift` L223](https://github.com/yazinsai/OpenOats/blob/HEAD/OpenOats/Sources/OpenOats/Models/TranscriptStore.swift#L223) and in batch re-transcription ([`BatchAudioTranscriber.swift` L620](https://github.com/yazinsai/OpenOats/blob/HEAD/OpenOats/Sources/OpenOats/Transcription/BatchAudioTranscriber.swift#L620)). [code]
- **Diarization:** FluidAudio `LSEENDDiarizer` on the *system* track only; mic is always "You" ([`DiarizationManager.swift` L1-L12](https://github.com/yazinsai/OpenOats/blob/HEAD/OpenOats/Sources/OpenOats/Transcription/DiarizationManager.swift#L1)). Core Audio tap: `AudioHardwareCreateProcessTap` in [`SystemAudioCapture.swift` L254](https://github.com/yazinsai/OpenOats/blob/HEAD/OpenOats/Sources/OpenOats/Audio/SystemAudioCapture.swift#L254). Also ships a Markdown meeting-format spec ([docs/meeting-format-spec.md](https://github.com/yazinsai/OpenOats/blob/HEAD/docs/meeting-format-spec.md)), useful as a reference for an Obsidian-friendly output format. Latest release v1.88.1.

### minutes (1.5k)
- Records mic and call audio as separate stems through a ScreenCaptureKit helper ([multi-source-capture.md L18, L267](https://github.com/silverstein/minutes/blob/HEAD/docs/architecture/multi-source-capture.md#L18)). The doc itself lists "Sidetone bleed... degrades attribution quality" and defers "Echo cancellation / sidetone cleanup (post-launch quality)" ([L151, L372](https://github.com/silverstein/minutes/blob/HEAD/docs/architecture/multi-source-capture.md#L151)).
- VPIO exists only for the **live voice assistant**: [`voice_live/voice_io.rs` L1-L10](https://github.com/silverstein/minutes/blob/HEAD/crates/core/src/voice_live/voice_io.rs#L1) ("Apple's VoiceProcessingIO unit captures and renders together and subtracts what it rendered from what it captured"). That is the same-unit reference model. [code]
- **Heuristic for bleed in diarization:** when the voice and system stem envelopes correlate >= `stem_correlation_threshold` (0.85) it collapses to one speaker. The config doc admits this "misfires for open-speaker mic setups" and tells users to raise it to 1.0 to disable ([`config.rs` L400-L410](https://github.com/silverstein/minutes/blob/HEAD/crates/core/src/config.rs#L400), [`diarize.rs` L1995-L2015](https://github.com/silverstein/minutes/blob/HEAD/crates/core/src/diarize.rs#L1995)). Lesson: a bleed detector must not be hard-wired to a single-speaker collapse. [code]
- Diarization: `pyannote-rs` with CAM++ (default) or WeSpeaker embeddings, with cosine `threshold` ([`config.rs` L390-L400](https://github.com/silverstein/minutes/blob/HEAD/crates/core/src/config.rs#L390), [`Cargo.toml` L18](https://github.com/silverstein/minutes/blob/HEAD/crates/core/Cargo.toml#L18)); voice enrollment config is `voice.match_threshold`. MCP server (`minutes-mcp`) exposes `search_meetings`. Latest release v0.28.2.

### Muesli (1.4k)
- **LocalVQE is the default meeting AEC; DTLN is the fallback** ([README L406-L410](https://github.com/Muesli-HQ/muesli/blob/HEAD/README.md#L406)). It uses the **v1.2 (1.3M-param, AEC+NS+dereverb) model** ([`LocalVQEProcessor.swift` L30](https://github.com/Muesli-HQ/muesli/blob/HEAD/native/MuesliNative/Sources/MuesliNativeApp/LocalVQEProcessor.swift#L30)), not the echo-only v1.4. The model is committed to the repo; the dylibs are built from LocalVQE at a pinned ref ([`scripts/build_localvqe.sh`](https://github.com/Muesli-HQ/muesli/blob/HEAD/scripts/build_localvqe.sh)). `MUESLI_AEC_PROCESSOR=localvqe-strict` disables the fallback. [code]
- **Streaming** with a processor protocol (`processFrame(mic:reference:)`), mic and tap on separate queues, and a **delay estimator**: envelope cross-correlation over candidate delays {0, 40, ..., 640, 720, 800} ms on 8 s windows every 2 s, with a confidence score. LocalVQE is given delay 0 ("soft delay estimation" in the model), DTLN gets the estimate ([`MeetingNeuralAec.swift` L540-L575, L242-L245](https://github.com/Muesli-HQ/muesli/blob/HEAD/native/MuesliNative/Sources/MuesliNativeApp/MeetingNeuralAec.swift#L540)). [code]
- Diarization is FluidAudio pyannote CoreML on the system audio only (README L79). Latest release v0.8.5 (2026-10-08).

### pasrom/meeting-transcriber (200; the closest design to ours)
- Records app audio ([CATapDescription](https://github.com/pasrom/meeting-transcriber/blob/HEAD/README.md#L85)) and mic as two 16 kHz tracks, queues transcription afterwards (`PipelineQueue`), and runs WhisperKit or Parakeet then FluidAudio diarization.
- **Echo design is documented in depth** in [CLAUDE.md L192-L212](https://github.com/pasrom/meeting-transcriber/blob/HEAD/CLAUDE.md#L192):
  - `EchoBleedDetector`: scores per-10 s-window envelope correlation between the tracks, centred on the recorder's own `micDelay`. The metric is "the share of 10 s windows above a correlation of 0.7", **not** whole-file correlation (the doc explains that whole-file dilutes partial bleed: 0.92 inside echo phases vs 0.657 over the file). Thresholds come from 86 real dual-source pairs: affected recordings at 34/60/77 % of windows, one borderline at 4 %, twenty clean at exactly 0 % ([`EchoBleedDetector.swift`](https://github.com/pasrom/meeting-transcriber/blob/HEAD/app/MeetingTranscriber/Sources/EchoBleedDetector.swift)). Verdict is three-state: `notMeasured` / `clean` / `affected`.
  - `LocalVQECanceller` ([`LocalVQECanceller.swift`](https://github.com/pasrom/meeting-transcriber/blob/HEAD/app/MeetingTranscriber/Sources/LocalVQECanceller.swift#L1)) + `PipelineQueue+EchoCancellation.swift`: **file-to-file**, mic 16 kHz mono + app track as reference, hop-by-hop through the C streaming API (256-sample hop), output has the same length as the mic; the mic track is rewritten in place (`mic_16k_cancelled.wav`) before anything else reads it. Alignment uses the recorder's `micDelay` as `referenceLead` ([`EchoCancelling.swift` L48-L74](https://github.com/pasrom/meeting-transcriber/blob/HEAD/app/MeetingTranscriber/Sources/EchoCancelling.swift#L48), [`PipelineQueue+EchoCancellation.swift` L64](https://github.com/pasrom/meeting-transcriber/blob/HEAD/app/MeetingTranscriber/Sources/PipelineQueue%2BEchoCancellation.swift#L64)). The model is `localvqe-v1.4-aec-200K-f32.gguf` (203K params, ~2.9 MB), bundled in the app, pinned by HF revision + SHA-256.
  - `EchoCancellationSelfCheck`: the cancellation is only adopted if the canceller's own per-window report shows a *difference* between windows with far-end audio and windows without. A level test is explicitly rejected because "a run that simply halves the microphone passes a level test". The failure it targets: "on a minority of recordings the model removes essentially nothing while completing normally". `echo.removed` is three-state (absent / false / true).
  - `EchoSegmentClassifier` (transcript dedup, **default off**): acoustic, not textual, explained-energy test. It is off because it removes a soft local speaker who talks over the far end, which `EchoSegmentClassifierTests` pins as an *expected failure*. A text-similarity rule would delete the user's own words when a far end replays them ("measured on a real call").
  - `EchoRemedy`: cancellation and dedup **do not compose**, so cancellation wins; the dedup only applies when cancellation did not actually happen.
  - `EchoEmbeddingQuarantine`: on an `.affected` recording the mic track's speaker embeddings are not written to `speakers.json`, because the stored voiceprints are running-mean centroids with no history.
- **Dual-track diarization** (each track separately) so the speaker list is not polluted by bleed. Voice embeddings are matched by cosine similarity across meetings. Latest release v0.8.1.
- **Limits I noted:** the cancellation is off by default and the author says a field soak is still pending. Only the first `echoBleedAnalysisSeconds` of a recording are analysed for the verdict, which "is a known limit".

### Biscotti (184, PolyForm Perimeter: source-available)

### Parrot (101, GPL-3.0)
- Realtime **SpeexDSP MDF** (`speex_echo_cancellation` + preprocess state linked to the echo state): 16 kHz, 160-sample frames, 2048-sample (128 ms) filter tail, reference = the SCK system-audio stream ([`EchoCanceller.swift` L1-L152](https://github.com/turantekin/Parrot/blob/HEAD/Parrot/Services/EchoCanceller.swift#L51)). On by default (`echoCancellationEnabled ?? true`, [`AudioCaptureManager.swift` L264](https://github.com/turantekin/Parrot/blob/HEAD/Parrot/Services/AudioCaptureManager.swift#L264)).
- The code's own comment ([L94-L97](https://github.com/turantekin/Parrot/blob/HEAD/Parrot/Services/EchoCanceller.swift#L94)): "FIFO pairing has no time alignment - mic/system clock drift walks it past the filter tail on long calls and cancellation decays to a no-op." This is the failure mode to avoid. GPL-3.0 means do not lift code.

### heed (18)
- Built **three** layers and measured them ([`ECHO_TUNING.md`](https://github.com/isjunrod/heed/blob/HEAD/eval_echo/ECHO_TUNING.md)): RMS gate, **WebRTC AEC3 via the LiveKit SDK** (`rtc.AudioProcessingModule`, [`transcription_server.py` L104-L127](https://github.com/isjunrod/heed/blob/HEAD/packages/transcription/transcription_server.py#L104)), and cross-channel text dedup (3-word windows, `difflib` ratio >= 0.63, [L216-L262](https://github.com/isjunrod/heed/blob/HEAD/packages/transcription/transcription_server.py#L216)).
- Result over 12 recordings (8 with echo), score = kept x (1 - echo): baseline 0.685; gate 0.627; gate + adaptive AEC 0.607; gate + always-on AEC 0.595; **text-dedup alone 0.730** (echo 0.000, user voice kept 0.77). AEC "cuts your own voice more than it removes echo". It is **single-user, n=12, realtime AEC3**, so it is a real signal but not proof against post-hoc neural AEC. Production config: dedup on, gate and AEC off.
- Diarization: Parakeet + Sortformer live; after stop, re-transcribe with per-token timestamps, WeSpeaker v2 256-d embeddings, cosine re-cluster, embeddings stored for "voice memory" ([README L249](https://github.com/isjunrod/heed/blob/HEAD/README.md#L249)). Latest release: none found via `gh`.

## Echo cancellation approaches

### What the problem looks like in our setup
Two tracks, no headphones: `mic.wav` = local voice + room + the speakers' output (the remote people, delayed 10s to 100s of ms and filtered by the room). `system.wav` = clean remote audio. Because `system.wav` is the *exact* far-end signal, offline AEC with it as reference is the textbook configuration. The only difficulty is time alignment (clock drift between the tap and the mic, Bluetooth output latency, speaker-to-mic acoustic path).

### A. Post-hoc / offline on the recorded tracks (recommended)

| Approach | Who | Notes |
|---|---|---|
| **LocalVQE neural AEC, file in / file out** | meeting-transcriber (default off); Muesli (streaming) | Apache-2.0 library + GGML, CPU, 16 kHz, 256-sample hop, "soft delay estimation". v1.4-AEC is 203K params, 0.83 ms per 16 ms hop on a Ryzen 9 7900 (~19x realtime) and "removes only the far-end echo and passes voice, room, and background through unchanged". On the ICASSP 2022 AEC blind test v1.4-AEC scores echo-MOS 4.20 / deg 2.45 on doubletalk. A CLI exists: `localvqe model.gguf --in-wav mic.wav ref.wav --out-wav enhanced.wav` ([README](https://github.com/localai-org/LocalVQE/blob/HEAD/README.md)). 229 stars, last push 2026-07-20, latest release v1.3 (2026-05-29). README says macOS is "expected to work", so it is not officially verified there; pasrom builds its own xcframework ([localvqe-xcframework](https://github.com/pasrom/localvqe-xcframework)) and Muesli builds the dylibs. |
| WebRTC AEC3 offline | screenpipe (live) | Works on files too, but the reference must be sample-aligned within the filter span. heed's evidence shows it can damage near-end speech. |
| SpeexDSP MDF offline | Parrot (live) | Classic adaptive filter, 128 ms tail. Cheap. Fine if the delay is aligned first and the tail covers the room. Weaker on reverberant echo (LocalVQE README says the same of its linear-only 2.7K build). |
| DTLN-aec (ONNX/CoreML) | anarlog, Muesli fallback | Neural, causal, small. Muesli's wrapper is `DTLNAecEchoProcessor`. |
| Linear subtraction with fitted gain | anarlog (`cancel_linear_echo`, as post-NN residual stage) | A single scalar gain per chunk is crude; useful only as a cleanup after a real AEC. |
| **Bleed detector as a gate** | meeting-transcriber | Envelope correlation between tracks at the recorder's known delay, 10 s windows, "share of windows > 0.7". Lets you skip AEC (and its near-end damage) on clean recordings. |
| **Transcript-level dedup** | OpenOats (Jaccard 0.78 / 1.75 s), heed (3-gram ratio 0.63), meeting-transcriber (acoustic, default off) | Zero audio damage, and heed's best scorer. Fails when the far end replays your words or when you interject over them. |

### B. Realtime (not our path, but mapped)
- **sonora / WebRTC AEC3** (screenpipe): timestamped queue alignment, bypass when no reference, 1 s queue cap ([`aec.rs`](https://github.com/screenpipe/screenpipe/blob/HEAD/crates/screenpipe-audio/src/core/aec.rs#L149)).
- **SpeexDSP** (Parrot): FIFO-paired, admits decay on long calls.
- **Neural**: anarlog (ONNX), Muesli (LocalVQE/DTLN).
- All of the live engines need a robust running delay estimate; Muesli's 0-800 ms candidate search and anarlog's +/-600 ms lag aligner are the concrete ranges seen in the wild.

### C. Apple VoiceProcessingIO (on the mic input)
What the projects found:

- **It works at the API level** (Biscotti L172-L202; minutes `voice_io.rs`; screenpipe opt-in; Scripta write-up).
- **Ducking:** Apple confirms that with voice processing on, "it will duck other audio that is not part of the voice processing output... another app is playing audio concurrently, its volume will be significantly reduced. This is intentional" ([Apple forums 829753](https://developer.apple.com/forums/thread/829753)). The control is `AVAudioInputNode.voiceProcessingOtherAudioDuckingConfiguration` (macOS 14+, `AVAudioIONode.h` L259-L267 in the local SDK, checked) with levels `default / min / mid / max` ([WWDC23 10235 notes](https://wwdcnotes.com/notes/wwdc23/10235)). **Workaround used:** `.init(enableAdvancedDucking: false, duckingLevel: .min)` (Biscotti; the Scripta author's write-up says it fixed ScreenCaptureKit system recordings that had gone "nearly silent at -51 dB", [dev.to](https://dev.to/thehwang/building-a-100-local-meeting-transcription-app-for-macos-with-whispercpp-and-screencapturekit-33m7)). The Audio Unit equivalent is `kAUVoiceIOProperty_OtherAudioDuckingConfiguration` (= 2108) with struct `AUVoiceIOOtherAudioDuckingConfiguration` and levels `kAUVoiceIOOtherAudioDuckingLevel{Default=0,Min=10,Mid=20,Max=30}` (I verified in `AudioToolbox/AudioUnitProperties.h` L2683-L2724 of the local SDK). No project in my sample sets it through the AU property; all use the AVAudioEngine property. **Even at `.min`, ducking is reduced, not proven to be zero** (I found no source that says it can be fully disabled).
- **Gotchas:** mic format silently becomes 9 channels (extract ch 0 manually); duplex unit faults unless the output side is driven at the matching rate; engine config-change handling; teardown order. OpenOats gave up: "conflicts with system audio capture... aggregate-device reconfiguration that can stall the mic stream" ([L525-L531](https://github.com/yazinsai/OpenOats/blob/HEAD/OpenOats/Sources/OpenOats/Transcription/TranscriptionEngine.swift#L525)). screenpipe saw VPIO streams that start but never deliver samples and built a demotion policy ([`vpio_health.rs`](https://github.com/screenpipe/screenpipe/blob/HEAD/crates/screenpipe-audio/src/device/vpio_health.rs#L1)).
- **Open question, unresolved: does VPIO's AEC cancel *other apps'* speaker output (Zoom playing through the speakers), or only what its own unit renders?** The evidence is split:
  1. Scripta (dev.to) reports enabling VPIO fixed the speaker-to-mic echo of ScreenCaptureKit-captured system audio **[empirical, single blog, not reproduced]**.
  2. screenpipe's comment says CoreAudio lists the *output device* used as the AEC reference in a VPIO process's input scope ([`macos.rs` L44-L48](https://github.com/screenpipe/screenpipe/blob/HEAD/crates/screenpipe-audio/src/core/meeting_audio/macos.rs#L44)), which suggests the reference is device-level output **[code comment, inferred]**.
  3. minutes describes the opposite model, "subtracts what it rendered" (same-unit render), for its voice assistant ([`voice_io.rs` L1-L10](https://github.com/silverstein/minutes/blob/HEAD/crates/core/src/voice_live/voice_io.rs#L1)); and Biscotti's NOTES.md said "echo-cancellation... needs an output reference we don't have" **[inference, not a measurement]**.
  The Apple forum thread does not address the reference. I lean toward "yes, it uses the device output" on the empirical evidence, but treat this as **unresolved until tested on our hardware**: record Zoom through the speakers with VPIO on and check whether the remote voice is attenuated in `mic.wav`.
- **Why I would still not use it for us:** (1) VPIO's output is processed (AGC, noise suppression, band-limiting, possible gating), so you lose the raw mic you would want for ASR, voiceprints and any later re-processing. (2) You cannot re-run it. (3) It fights the process tap (OpenOats), changes the system's output volume behaviour, and can silently die (screenpipe). (4) With two clean tracks saved, we have an offline option that is rerunnable and tunable.

### D. Not-AEC mitigations worth keeping
- **Headphone detection -> skip AEC** (anarlog `headphone_only_output()`); avoids the near-end damage measured by heed.
- **Embedding quarantine** (meeting-transcriber): never write a mic-track voiceprint from a recording flagged as bled.
- **Dual-track diarization** so bleed cannot create phantom speakers; **do not** auto-collapse tracks on high correlation (minutes' 0.85 rule misfires on open speakers).

### Recommendation for our two-track, offline setup

1. **Capture raw.** Mic through plain AVAudioEngine/HAL (no `setVoiceProcessingEnabled`), system through the process tap, same host clock; record the start offset of each track (our equivalent of `micDelay`).
2. **Post-process in Python** (per meeting):
   a. Resample both to 16 kHz mono.
   b. **Bleed detector:** per-10 s window envelope correlation at the best lag (search 0-800 ms, as Muesli does); verdict = share of windows with correlation > ~0.7 (pasrom's numbers; recalibrate on our recordings). Clean -> skip AEC, tag `echo: clean`.
   c. If affected: **LocalVQE v1.4-AEC** (echo-only; the right choice because ASR follows and we do not want the room deleted) via the C library/CLI with `system.wav` (delay-compensated by the estimated lag) as reference. v1.2/v1.3 also remove noise and reverb, which may help or hurt Whisper/Parakeet; test both. Use the CLI (`localvqe model.gguf --in-wav mic.wav ref.wav --out-wav out.wav`) or ctypes/cffi over `liblocalvqe`.
   d. **Self-check** as pasrom does: compare energy on far-end-active windows vs far-end-silent windows before/after; if it removed nothing, flag it and fall back.
3. **Fallback only on `affected` + failed/absent cancellation:** a conservative text-dedup. Prefer the acoustic version (explained-energy) over Jaccard; if you use Jaccard, restrict to mic-after-remote within ~2 s, >= 4 words, and mark rather than delete (pasrom's finding that deleting audio ate local words during double talk). **Never stack cancellation and dedup.**
4. **Validate before trusting:** assemble 10-20 of our own meetings with ground truth, score `echo_in_mic` and `own_voice_kept` the way heed did (kept x (1 - echo)). That is the only protection against both heed's "AEC hurts" result and LocalVQE's "removes nothing on some recordings" failure.
5. **Diarize each track separately** (see below) and quarantine mic embeddings on affected meetings.

Residual risks I did not test: LocalVQE on macOS is community-built; v1.4-AEC's quality on non-16 kHz-native speech is not benchmarked beyond the ICASSP set; Bluetooth output (100-200 ms) must fall inside the delay search; I have not run any of this code.

## Diarization / voiceprint approaches

| Project | Models / libs | Mode | Persistent identity |
|---|---|---|---|
| meeting-transcriber | FluidAudio: `OfflineDiarizer` or Sortformer (overlap-aware), Silero VAD | **Dual-track**, offline | `speakers.json`, embeddings folded into running-mean centroids, cosine match; user-confirmed names; quarantined on echo-affected recordings |
| Biscotti | Argmax SpeakerKit (pyannote) + WhisperKit | offline | Voiceprints compared with past labeled meetings; a third LLM step arbitrates (greetings, calendar attendees) ([README L101-L102](https://github.com/scosman/Biscotti/blob/HEAD/README.md#L101)) |
| heed | Parakeet + Sortformer (live); WeSpeaker v2 256-d recluster (post) | live then post | Stored embeddings ("voice memory") |
| minutes | pyannote-rs, CAM++ / CAM++_LM / WeSpeaker ResNet34 (community-1 set) | offline | Voice enrollment, `voice.match_threshold`; note CAM++_LM needs a lower threshold (~0.1-0.2) |
| anarlog | own `pyannote-local` (segmentation + clustering) | offline batch | `KnownSpeaker` / `SpeakerIdentity` types; manual speaker selector in the UI |
| Muesli | FluidAudio pyannote CoreML | after the meeting, system audio only | not documented |
| OpenOats | FluidAudio LS-EEND (DIHARD3 variant), streaming | live, system track only | local labels to names map only |
| screenpipe | pyannote segmentation + embedding ONNX | continuous | embedding manager (not traced) |
| Meetily CE | none | n/a | PRO only |

Takeaways for us:
- The mac-native stacks converge on **FluidAudio (CoreML/ANE) + Parakeet/WhisperKit**. We run a Python pipeline, so the equivalents are pyannote.audio 3.x/community-1, WeSpeaker/CAM++ embeddings, or NeMo Sortformer; all of them are used by the projects above, so there is no exotic dependency.
- **Dual-track diarization is the design that sidesteps bleed for speaker separation.** The mic track is (almost) one person: label it as the user, run diarization only on the system track, and use voiceprints to name remote speakers. Where the user is not alone at the mic (in-person), diarize the mic track too.
- **Voiceprint hygiene**: store embeddings with provenance (track, echo verdict), use a running-mean centroid only from clean audio (pasrom's quarantine), and keep a per-speaker sample count so a bad merge is recoverable. Biscotti's extra LLM arbitration step on top of the voiceprint match is a reasonable pattern with Claude in our pipeline.
- Expect to tune the cosine threshold per embedding model (minutes' note on CAM++_LM).
